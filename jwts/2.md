从你 `2.txt` 看，问题不是“刚开始都是正常后来坏了”，而是这些服务启动后不久就重启了：

```text
course-service     0/1 Running RESTARTS 1
gateway-service    0/1 Running RESTARTS 1
student-service    0/1 Running RESTARTS 1
teacher-client     0/1 Running RESTARTS 1
teacher-service    0/1 Running RESTARTS 1
```

`0/1 Running` 的含义是：容器进程当前在运行，但没有通过 readiness，就绪失败。`RESTARTS 1` 说明之前已经退出/被杀过一次。

最可疑点有两个：

1. 这些异常 Pod 全在 `k8s-worker2`
2. 多个 Java 服务同时 `0/1`，很可能是 `worker2` 资源不足，或者 readiness/liveness 探针过早把它们杀掉

先按下面排查，不要先乱删。

**1. 看 worker2 是否资源不足**

```bash
kubectl describe node k8s-worker2 | grep -A8 "Allocated resources"
kubectl describe node k8s-worker2 | grep -A5 "Conditions"
```

如果装了 metrics-server：

```bash
kubectl top node
kubectl top pod -n jwts
```

**2. 看某个失败服务的真实原因**

先看 `student-service`，它最可能还涉及 MySQL：

```bash
kubectl logs -n jwts deployment/student-service --previous --tail=120
kubectl logs -n jwts deployment/student-service --tail=120
kubectl describe pod -n jwts student-service-5b79574d4d-qscvw | tail -60
```

再看网关：

```bash
kubectl logs -n jwts deployment/gateway-service --previous --tail=120
kubectl describe pod -n jwts gateway-service-d49b8c5d6-krqf6 | tail -60
```

重点找：

```text
OOMKilled
Liveness probe failed
Readiness probe failed
Caused by
Communications link failure
Connection refused
Unknown database
Access denied
```

**3. 先临时取消所有服务探针，确认是不是探针导致**

你现在的服务启动慢，探针很容易误杀。可以先取消异常服务的探针：

```bash
for d in student-service teacher-service course-service teacher-client gateway-service; do
  kubectl patch deployment "$d" -n jwts --type=strategic -p='
{
  "spec":{
    "template":{
      "spec":{
        "containers":[{
          "name":"'"$d"'",
          "readinessProbe":null,
          "livenessProbe":null,
          "startupProbe":null
        }]
      }
    }
  }
}'
done
```

然后重启这些 Deployment：

```bash
for d in student-service teacher-service course-service teacher-client gateway-service; do
  kubectl rollout restart deployment "$d" -n jwts
done

kubectl get pods -n jwts -w
```

如果取消探针后都变成 `1/1 Running` 且 `RESTARTS` 不再增加，说明主要是健康检查设置太急，不是业务代码坏了。

**4. 给 Java 服务限制堆内存**

多个 Java 服务堆内存不限制，在小虚拟机上很容易把节点顶爆：

```bash
for d in student-service teacher-service course-service student-client teacher-client course-client gateway-service; do
  kubectl set env deployment/"$d" -n jwts JAVA_OPTS="-Xms128m -Xmx384m"
done
```

Eureka 可以稍大一点：

```bash
kubectl set env deployment/eureka-service -n jwts JAVA_OPTS="-Xms128m -Xmx512m"
```

然后重启：

```bash
kubectl rollout restart deployment -n jwts
kubectl get pods -n jwts -w
```

**5. 确认数据库**

业务 service 依赖 MySQL，确认表在：

```bash
MYSQL_POD=$(kubectl get pods -n default -o name | grep mysql | head -n 1)

kubectl exec -it -n default "$MYSQL_POD" -- \
mysql -uroot -proot -e "USE jwts_db; SHOW TABLES;"
```

**6. 最关键判断**

如果 `--previous` 日志里是：

- `OOMKilled` 或退出码 `137`：worker2 内存不够，减少同时部署数量或给虚拟机加内存
- `Liveness probe failed`：探针误杀，删除探针或加 `startupProbe`
- `Communications link failure`：MySQL 访问不通
- `Access denied`：数据库账号密码错
- `Unknown database jwts_db`：SQL 没导入

你现在先跑这两条最有价值：

```bash
kubectl logs -n jwts deployment/student-service --previous --tail=120
kubectl describe pod -n jwts student-service-5b79574d4d-qscvw | tail -60
```

它们基本能把原因钉住。
