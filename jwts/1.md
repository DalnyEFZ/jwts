问题大概率在这里：你前面为了排查重启，删除了 `readinessProbe/livenessProbe`。所以现在 `READY 1/1` 只代表“容器进程还活着”，不代表 Eureka 的 `8888` 已经真正启动。

你贴的日志里还没有看到关键成功行：

```text
Undertow started on port(s): 8888
Started EurekaServiceApplication
```

所以浏览器访问 `192.168.186.10:30001` 被拒绝，是因为 Eureka 应用还没监听 8888，或者 NodePort 没配通。

先在 Master 执行这几步定位：

```bash
POD=$(kubectl get pod -n jwts -l app=eureka-service -o jsonpath='{.items[0].metadata.name}')

kubectl exec -n jwts "$POD" -- sh -c \
'cat /proc/net/tcp /proc/net/tcp6 | grep -i ":22B8" && echo "8888已监听" || echo "8888没监听"'
```

如果显示 `8888没监听`，说明 Eureka 还没启动完成。继续看日志：

```bash
kubectl logs -n jwts "$POD" --tail=200 -f
```

如果一直不出现 `Started EurekaServiceApplication`，建议直接重启并给足资源：

```bash
kubectl set env deployment/eureka-service -n jwts JAVA_OPTS="-Xms128m -Xmx512m"

kubectl patch deployment eureka-service -n jwts --type=merge -p='
{
  "spec":{
    "template":{
      "spec":{
        "containers":[{
          "name":"eureka-service",
          "resources":{
            "requests":{"cpu":"500m","memory":"512Mi"},
            "limits":{"cpu":"2","memory":"1Gi"}
          }
        }]
      }
    }
  }
}'
```

然后重启：

```bash
kubectl rollout restart deployment/eureka-service -n jwts
kubectl logs -n jwts deployment/eureka-service -f
```

等看到：

```text
Undertow started on port(s): 8888
Started EurekaServiceApplication
```

再测试：

```bash
curl http://$(kubectl get pod -n jwts -l app=eureka-service -o jsonpath='{.items[0].status.podIP}'):8888/
curl http://$(kubectl get svc eureka-service -n jwts -o jsonpath='{.spec.clusterIP}'):8888/
curl http://192.168.186.10:30001/
```

如果 Pod IP 能访问，但 `30001` 不能访问，再查 Service：

```bash
kubectl get svc,endpoints -n jwts
```

`eureka-service` 应该显示：

```text
8888:30001/TCP
```

另外，你的 `application.yml` 里有：

```yaml
eureka:
  instance:
    hostname: 127.0.0.1
```

在 Kubernetes 里不建议写 `127.0.0.1`，建议删掉或注释掉，只保留：

```yaml
eureka:
  instance:
    prefer-ip-address: true
```

但当前“拒绝连接”的直接原因，优先看 8888 是否监听。现在的 `READY 1/1` 不可靠，因为探针被删了。
